# Vtiger BS3→BS5 Migration Reference

Full log of the modernization work on this vtiger 8.4 install: what changed, why, and what's still pending. Read this before touching Bootstrap/jQuery-related code in this repo so you don't redo work or reintroduce a fixed bug.

**⚠️ Trust git history over this log, always.** On 2026-09-22 this log claimed the class-rename sweep and JS API conversion were both complete app-wide. They weren't — git history had only 4 commits total, touching a narrow slice of files (mostly `Vtiger/` core + `helper.js`/`application.js`/`app.js`), while live grep found ~230 template/JS files across nearly every module still on raw Bootstrap 3 markup, including `helper.js`/`Tag.js`/`Utils.js` themselves — the exact files this log said were "most central, already converted." The work described below as done was re-verified against the actual repo state on 2026-09-22 and is now accurate as of that date. If you're reading this later and something looks unswept, believe the grep, not the log — run `git log --oneline -- <file>` and a fresh grep before assuming a past session's claims here are still true.

## Class/attribute renames — swept app-wide across `layouts/v7/modules` + `layouts/v7/resources` (verified 2026-09-22), don't redo

|---|---|---|

| `data-dismiss="..."` | `data-bs-dismiss="..."` | Missed in the original pass — 68 occurrences found later, all real (modal/alert close buttons) |

| `.navbar-right` | `margin-left: auto` (custom CSS) | BS5 has no equivalent class — **no markup changes needed**, just add `.navbar-right { margin-left: auto; }` to `nav.css`; the class stays in the markup as a pure CSS hook |

**JS-side attribute reads must be updated in lockstep with the markup rename**, or they silently break: `.data('toggle')` (jQuery camelCases `data-bs-toggle` to `bsToggle`, not `toggle`) and `[data-toggle]` selectors stop matching once markup says `data-bs-toggle`. Found and fixed in `Vtiger/ListSidebar.js`, `Vtiger/AdvanceSearchList.js`, `Vtiger/SearchList.js`, `Vtiger/List.js`, `Reports/List.js`, `Reports/ChartDetail.js`.

If you find an un-swept instance, it's a real bug. Do a full-tree grep before assuming it's already handled — don't trust a prior sweep's claimed file count.

## Critical structural fixes (not obvious, easy to miss)

**`navbar-expand-lg` is required on `<nav class="app-fixed-navbar">`.** Without any `.navbar-expand-*` class, BS5 keeps `.navbar-collapse` content (search box, quick-create, user menu — basically the whole right side of the top bar) hidden at ALL widths. BS3 auto-showed this above a breakpoint via CSS baked into `.navbar-collapse` itself; BS5 requires explicit opt-in via `.navbar-expand-{breakpoint}`.

**Side effect:** `navbar-expand-lg` also sets `flex-wrap: nowrap` on the nav. This vtiger markup stacks TWO separate `.container-fluid` blocks inside one `<nav>` (top user bar + breadcrumb bar below it) — `flex-wrap:nowrap` forces them onto one line, splitting the nav's width ~50/50 between them instead of stacking. Fix (applied in `layouts/v7/lib/modern/css/nav.css`):
```css
.app-fixed-navbar.navbar-expand-lg { flex-wrap: wrap !important; }
```

**`.navbar-right` and `float-end` on flex children:** `.nav` is `display:flex` in BS5, and floats have no effect on flex items. `.navbar-right` (BS3 float helper) also doesn't exist in BS5. Fix (applied in `nav.css`, no markup changes): `.navbar-right { margin-left: auto; }` — covers all 12 occurrences (`ModuleHeader.tpl`/`CalendarHeader.tpl`/`ListViewHeader.tpl`/`Topbar.tpl` across modules).

**`.caret` markup duplicates BS5's own arrow.** BS5's `.dropdown-toggle` auto-draws an arrow via CSS `::after`. Old markup still has literal `<span class="caret">`/`<i class="caret">` in 31 files — don't try to restyle it, just hide it (applied in `nav.css`): `.caret { display: none; }`.

**Popper is required for dropdowns/tooltips/popovers to position correctly.** Load `bootstrap.bundle.js` (includes Popper) or load Popper separately before plain `bootstrap.js`.

## jQuery 3 regressions found and fixed

- `.size()` → `.length` (`.size()` removed in jQuery 3)
- `.live()` → `.on()` (delegated event binding; `.live()` fully removed)
- `$.browser` fully removed. Real code (`PrintReport.tpl`) and vendor code (jqplot) both depended on it. Fix: a global shim right after jQuery loads — `jQuery.browser = jQuery.browser || {};` — stops crashes without restoring real detection (fine, since no modern browser is IE anyway).
- `jQuery(window).load(fn)` is ambiguous with jQuery's AJAX `.load()` method in jQuery 3 and doesn't reliably bind as a window-load event. Fix: `jQuery(window).on('load', fn)`.
- jstorage plugin deletion broke internal wrapper functions in `application.js` (`storage.get/set/delete/flush`) and root `resources/app.js` (`cacheGet/cacheSet/cacheClear`) — both rewritten to call native `localStorage` directly. **Lesson: check for internal wrapper dependents before deleting any plugin, not just external template/module usage.**

## BS5 JS API — jQuery-plugin calls converted to vanilla JS classes

BS5 removed the jQuery-plugin style entirely (`$(el).modal('show')` etc no longer works out of the box). **Explicit project decision: no compatibility shim — direct call-site rewrites in every file.** A shim (monkey-patching `jQuery.fn.modal` etc to delegate to BS5 classes) was proposed and rejected.

Conversion patterns used throughout:

| Old call | New call |
|---|---|
| `X.modal(options)` | `bootstrap.Modal.getOrCreateInstance(X[0], options).show();` |
| `X.modal('hide')` | `var _m = bootstrap.Modal.getInstance(X[0]); if(_m) _m.hide();` |
| `X.tooltip(options)` | `bootstrap.Tooltip.getOrCreateInstance(X[0], options);` |
| `X.popover(options)` | `bootstrap.Popover.getOrCreateInstance(X[0], options);` |
| `X.popover('show'/'hide'/'toggle')` | `var _p = bootstrap.Popover.getInstance(X[0]); if(_p) _p.show()/.hide()/.toggle();` |
| `X.popover('destroy')` | `var _p = bootstrap.Popover.getInstance(X[0]); if(_p) _p.dispose();` |
| `X.dropdown('toggle')` | `bootstrap.Dropdown.getOrCreateInstance(X[0]).toggle();` |
| `X.collapse('show'/'hide')` | `bootstrap.Collapse.getOrCreateInstance(X[0]).show();` or via `getInstance().hide()` |

All 20 affected app-code files (vendor/lib excluded from scope) have been converted, verified 2026-09-22: `helper.js` (most central — 10 modal calls), `Emails/MassEdit.js`, `Emails/EmailPreview.js`, `Settings/Workflows/Edit.js`, `Vtiger/Utils.js`, `Settings/CustomerPortal/CustomerPortal.js`, `Vtiger/ListSidebar.js`, `Vtiger/Detail.js`, `Vtiger/List.js`, `Vtiger/Tag.js`, `Calendar/TaskManagement.js`, `MailManager/List.js`, `Settings/SMSNotifier/List.js`, `Settings/ExtensionStore/ExtensionStore.js`, `Products/Detail.js`, `Inventory/Detail.js`, `Inventory/Edit.js` (25 calls, same handful of patterns repeated — 4 more are inside a comment, `// chargesTrigger.popover('hide');` etc, deliberately left alone), `Leads/Detail.js`, `Potentials/Detail.js`. `Vtiger/validation.js` had a `.popover()` block that turned out to be dead/commented code — skipped, don't "fix" commented-out code.

Extra nuances hit during conversion, worth knowing before doing more of these:
- **Multi-element selectors need `.each()`**, not `X[0]`: class/attribute selectors like `jQuery('[rel="tooltip"]')` or `jQuery('.totalCostCalculationInfo')` can match more than one node — `getOrCreateInstance` takes exactly one element. Single-element cases (an ID selector, or a variable already scoped to one node via a click handler's `e.currentTarget`) are safe to use `X[0]` directly.
- **`.data('bs.popover').tip()` has no BS5 equivalent.** Old code used this to grab the generated tip element synchronously right after init. BS5 doesn't expose `.tip()`; instead, hook `shown.bs.popover` and read `element.attr('aria-describedby')` to find the actual tip element in the DOM (`Products/Detail.js`).
- **`.removeData("modal").modal(newParams)` (force re-init with fresh options)** becomes: `getInstance(...)?.dispose()` first, then `getOrCreateInstance(el, newParams).show()` — `getOrCreateInstance` reuses an existing instance's original config if one exists, so you must dispose before re-creating with different params (`helper.js` `showModal`/`hideModal`, `Emails/MassEdit.js`).
- **The old sanitizer whitelist API renamed**: `X.popover.Constructor.DEFAULTS.whiteList` (BS3/4, per-instance) → `bootstrap.Popover.Default.allowList` (BS5, static on the class, and renamed `whiteList`→`allowList`) (`MailManager/List.js`).
- Guard `getOrCreateInstance`/`getInstance` calls with a null/existence check wherever the original jQuery selector could legitimately match nothing (e.g. `#phoneFormatWarningPop` only exists on modules with phone fields) — jQuery silently no-ops on an empty selection, but `bootstrap.Popover.getOrCreateInstance(undefined)` throws.

If you find more `.modal(`/`.tooltip(`/`.popover(`/`.dropdown(`/`.collapse(` calls in app code (not vendor `/lib/` folders), convert them the same way.

## Debugging approach that works here

1. Pull the latest repo state before diagnosing (`git pull`; watch for local uncommitted test edits blocking the pull).
2. When something "still looks broken after the fix," check in this order: (a) was the fix actually applied/pushed, (b) is Smarty cache stale, (c) is browser cache stale (`?v=8.4.0` doesn't bust Smarty server-side cache).
3. For layout bugs, get real computed-style data via browser DevTools console (`getComputedStyle`, `getBoundingClientRect`) rather than guessing from screenshots repeatedly — this found the exact `flex-wrap:nowrap` 50/50-split bug fast once real numbers were in hand.
4. Read the actual rendered HTML output when available (view-source or a pasted DOM dump) — this is far more reliable than reasoning about what the templates "should" produce, especially once several rounds of edits have happened.
5. **CSS comment gotcha discovered 2026-09-22, twice in one session: never write a file-glob path like `skins/*/style.css` inside a `/* ... */` comment.** The substring `*/` embedded in `/*/` closes the comment early, silently turning the rest of the intended comment text into garbage CSS tokens that swallow the real rule immediately after it — the rule doesn't error, it just vanishes from the parsed stylesheet (`document.styleSheets` won't show it at all). This happened twice in the same editing session (once in `listview.css`'s `body` rule, once in `nav.css`'s navbar `z-index` rule) and both times manifested as "I wrote the !important fix but the browser still shows the old value" — which looks identical to a browser-cache problem, wasting time chasing the wrong cause. Always verify a suspicious missing rule by checking `document.styleSheets[i].cssRules` directly (not just `getComputedStyle`) when a fix "isn't applying" despite `!important` and a confirmed-correct file on disk. Write "skins subfolder's style.css" or similar in prose instead of the literal glob.

## Per-app skin files silently override the modern layer (2026-09-22)

Discovered while chasing several "already fixed but still broken" reports: `layouts/v7/skins/{marketing,sales,inventory,contact,project,support,tools,marketing_and_sales}/style.css` (one loaded per active "app"/module-group context, all near-identical copies of the original BS3-era skin) load **after** `nav.css`/`listview.css`/`editview.css`/`detailview.css` and still carry a large amount of original BS3 styling for shared class names our modern layer also targets. Where specificity is equal (same selector, e.g. bare `body` or single-class `.close`), the skin's later-loaded rule silently wins — a fix can be 100% correct in the modern CSS and still not appear live, with no error anywhere, because a different property value from the skin cascades in in its place.

Confirmed real conflicts found this session (all fixed with `!important` in the modern-layer file rather than editing 8 skin files):
- `body{font-family:OpenSans-Regular,sans-serif;font-size:12px}` — overrode the Roboto/Sora font-family choice on **every page**, app-wide. This was the actual root cause of "fonts inconsistent everywhere."
- `.btn-success{font-size:12px;padding:2px 6px}` — cramped every success/primary button on marketing-skinned pages.
- `.cancelLink, .popoverCancel{padding-left:10px;color:red}` — partially fought the new Cancel-button styling.
- `.close{color:#c3c3c3 / #fff / #000}` (three different rules depending on context) — close-icon color varied by which skin/page you were on.
- `.search-link{border:thin solid #DDD;float:left;margin:4px}` — gave the dark navbar's search box a stray light-gray border and BS3 float layout.
- `.quickCreateContent .input-group{display:table}` — squeezed Quick Create's date/time inputs down to ~22px wide (higher specificity than a bare `.input-group`, so this one wasn't even an equal-specificity fight — it won outright).
- `.module-nav{z-index:1093}` (the left sidebar — both the Settings menu and the module-icon rail share this class) — higher than BS5's own `.fixed-top` navbar (`z-index:1030`), so the sidebar rendered on top of the navbar's logo/hamburger corner once a page scrolled far enough. Fixed by raising the navbar to `z-index:1094` in `nav.css` — deliberately *not* higher than that, since `#helpPageOverlay` (the right-sliding Quick Preview panel) sits at `z-index:1099` by design, on top of the navbar, so its own header/close button aren't buried when open. Order that matters: sidebar `1093` < navbar `1094` < quick-preview overlay `1099`.
- `#helpPageOverlay{width:300px;right:0px}` (correct, right-anchored by design) vs BS5's `.modal{left:0px}` (different property, so not a specificity conflict — **both applied simultaneously**). With an inline `width:550px` also set, having both `left:0` and `right:0` pinned over-constrains the box, and per the CSS positioning spec the browser drops `right` and anchors via `left` — this is why the Quick Preview slide-in panel opened from the **left** instead of the right. Fixed with `#helpPageOverlay.modal{left:auto !important}`.

**Lesson for future work on this codebase:** when a fix "doesn't seem to apply" and the file on disk is confirmed correct, check `document.styleSheets` for the *actual* winning rule before assuming a cache issue — there's a good chance one of the 8 skin files is the real culprit, not staleness. This class of bug is probably not fully exhausted; if another shared classname turns up unstyled or inconsistently styled despite a rule existing in the modern layer, check the skin files before anything else.

**Design.** Server contract unchanged: positions are `{"row","col"}` (1-based) and sizes `{"sizex","sizey"}` in `vtiger_module_dashboard_widgets`. - **Place, then reflow.** Saved widgets are placed first (reading order) into the full 4-column space exactly as saved, then `grid.onResize()` reflows to the window width with layout `compact`. Clamping widgets one by one at init makes them collide and push each other down (History, the 2×2, ended up on row 4). Never-positioned widgets (`data-position="false"`) are placed afterwards with `autoPosition`.
- **Save only after a user action, and only at 4 columns.** The old code saved on every load; with saving finally working that would persist whichever device loaded first (a phone would store a 1-column layout). Below 4 columns the grid is `setStatic(true)` (read-only reflow; add/remove still work) and `persistLayout()` returns early. Constant: `Vtiger_DashBoard_Js.fullGridColumns`. **Open decision:** laptops at 1280–1366px (3 columns) can view but not rearrange; the richer option is to store a layout per column count in the same `position` JSON.

## PHPExcel → PhpSpreadsheet (2026-10-04)

**Done.** `libraries/PHPExcel` (3.7 MB, 202 files, ~203 PHP 8.4 deprecations) is deleted. **Fixed as a side effect.** The old library printed hundreds of deprecation lines on a cold start, and because `Content-Length` is taken from the temp file, a Reports → Export XLS download could arrive as truncated `<br /><b>Deprecated…` HTML. **API changes you must know when touching this code.**
- Cell coordinates are `[column, row]` and **1-based** (PHPExcel's `...ByColumnAndRow` took 0-based columns, hence the `$count + 1`).
- `setCellValueExplicit()` has no default data type; always pass `DataType::TYPE_STRING` or `TYPE_NUMERIC`. The old header call passed `true` as the type, which PHPExcel happened to treat as a string.
- Style arrays use `fillType`/`startColor`, not `type`/`color`.
- **`TYPE_NUMERIC` now throws on a non-numeric value** (PHPExcel did `(float)$value`, so a formatted `1,234.50` silently became `1` and `$12.00` became `0`). The export now writes a numeric cell only when `is_numeric($value)` and otherwise a text cell, so the displayed value is never wrong. A blank numeric value is now an empty cell, where it was `0` before.
- The `ob_clean()` that guarded against stray output now runs only when an output buffer is active (it raised a notice without one).

**How it was verified (reusable).** A CLI harness (scratchpad `export_report.php`, bootstrapped like `vtigercron.php`: `vendor/autoload.php`, `config.php`, `EntryPoint`, active admin, explicit `require_once 'modules/Reports/ReportRun.php'`) exported **all 25 reports** with the old code (that one file stashed) and the new code, and a second script compared every cell value, cell type and header fill through PhpSpreadsheet's reader: 0 differences (14 reports had data; 136 text cells, 8 numeric cells, fill `E1E0F7`). ## GSTIN validation on Accounts — 2026-10-04

**What it does.** A GSTIN saved on an Account must be well formed (15 characters: 2-digit state code from the GST table, 10-character PAN, entity number, `Z`, check character) **and** its check character (a base-36 weighted checksum over the first 14 characters) must match, so a mistyped digit is caught as well as a malformed number. Empty is fine. A valid value is stored upper-case without spaces.
- **Server (authoritative):** `AccountsGSTINHandler` (`modules/Accounts/AccountsGSTINHandler.php`), a `vtiger.entity.beforesave` handler registered by `bin/add-account-gstin.php` (idempotent; the registration is a row in `vtiger_eventhandlers`, so run `bin/dump-db.sh` to carry it into `db/schema.sql`). It covers every save path: edit form, quick create, inline edit, import, webservice. The rules are `Vtiger_GST_Utils::gstinProblem()` / `hasValidCheckCharacter()`.
- **Edit form:** `Accounts_Edit_Js.registerGstinValidation()` upper-cases and trims on blur, and on Save refuses an invalid number with a red message beside the field (no round trip). `gstinProblem()` there mirrors the PHP rules; the two were run on the same 16 inputs and agree.
- The PDF's `isValidGSTIN()` stays format-only (it is used to pick the "GSTIN:" label, not to reject), so a stored number is never hidden from a printout.

**Verified in the running app** (account 6, restored to its original NULL afterwards): the form blocks `27AAPFU0939F1ZW` (wrong check character) with the message beside the field and leaves the database untouched; ` 27aapfu0939f1zv ` is shown as `27AAPFU0939F1ZV` on blur and stored that way; the server-side `SaveAjax` path rejects `BADNUMBER12345` with the message, stores `19aamcd3313n1zb` as `19AAMCD3313N1ZB`, and accepts clearing; an ordinary save with no GSTIN still works. Known-valid GSTINs used for the checksum: `27AAPFU0939F1ZV` and `19AAMCD3313N1ZB`.

**Mistake worth remembering.** `VTEntityData::getData()` returns a `TrackableObject` (ArrayAccess), not an array: `array_key_exists()` on it is a fatal TypeError, and because the handler is global that made *every* Accounts save fail until it was fixed (a few minutes, caught by the first UI test). Use `isset($data['field'])`. Register a before-save handler only after testing it on an ordinary save, or test it in a CLI harness first.

**Limits.** Entities with non-standard identifiers (for example UN bodies or embassies, whose numbers do not follow the 15-character layout) cannot be saved in this field; the check also cannot tell whether a well-formed number is actually registered (that needs the GST portal).

## Credit / Debit Notes in the Sales Order module — 2026-10-09

**Decision.** The user wanted the existing Sales Order module reused as the credit/debit note module (credit note = against an Invoice, customer side; debit note = against a Purchase Order, vendor side). A separate `CreditNote` module was built first (2026-10-05) and then retired (`bin/remove-credit-note-module.php`). The internal name stays `SalesOrder` (URLs, permissions, line-item engine, tables); labels are "Credit/Debit Notes" / "Note No" / "Note Date" (`languages/en_us/SalesOrder.php`, `vtiger_field.fieldlabel`).

**Database conversion: `bin/convert-salesorder-to-notes.php`** (idempotent; applied to the real DB 2026-10-09 after a backup, 0 orders existed). Hides the order-only fields (presence 1), makes the account optional, adds `note_type` (picklist), `invoice_id`, `vendor_id`, `purchaseorder_id` (uitype 10) and `reason`, status values Created/Approved/Sent/Cancelled, number series CN (`SalesOrder` row) and DN (`SalesOrderDebit` row, picked by `SalesOrder::setModuleSeqNumber()` from `note_type`), list columns, related lists (Credit Notes on Invoice, Debit Notes on Purchase Order), registers `SalesOrderNoteHandler`, and **drops the leftover foreign key `vtiger_salesorder.vendorid -> vtiger_vendor`** (it rejected the 0 stored for "no vendor", so every credit note silently failed to insert).

**Rules.** `modules/SalesOrder/SalesOrderNoteHandler.php` (beforesave): credit note needs account + invoice, debit note needs vendor; then `Vtiger_Note_Utils::saveProblem()` (`include/utils/NoteUtils.php`): the invoice/PO must be in an eligible status (Invoice: Approved, Sent, Credit Invoice, Paid; PO: Approved, Delivered, Received Shipment), the customer/vendor must match the document, return notes (reason Sales Return / Purchase Return) cannot exceed the quantity still open per product (earlier non-cancelled notes of the same type count), and all notes together cannot exceed the document total. `creationProblem()` also decides whether the "Create Credit Note" (Invoice) / "Create Debit Note" (Purchase Order) buttons are shown, and `Edit.php` refuses a direct URL. Prefill (`SalesOrder_Edit_View::limitLineItemsFromParent`) starts with the open quantities; the JS recalculates totals on load.

**Create from a document.** `Inventory_Edit_View` branch for `SalesOrder` with `invoice_id` / `purchaseorder_id`, plus two hooks (`prefillFromParentRecord`, `limitLineItemsFromParent`). Edit.js (`registerNoteTypeEvents`) shows only the fields of the chosen type.

**PDF.** `Vtiger_SalesOrderPDFController` by note type: "Credit Note: CN…" / "Debit Note: DN…", customer or vendor, reason, "Against Invoice/Purchase Order" number and date, GSTIN row labelled Customer/Vendor GSTIN. The GST print is on for `SalesOrder` (`moduleHasGstPrint`).

## Product Categories and Payments modules — 2026-10-09

Both are ordinary vtlib modules built from the module-designer template (`Vtiger_CRMEntity` subclass in `modules/<Name>/<Name>.php`, language file, one idempotent registration script; no `views/`/`models/` needed, the `Vtiger_*` fallbacks apply). Developed and verified in the sandbox; **apply to the real DB with a backup** (`php bin/create-product-categories-module.php`, `php bin/create-payments-module.php`, then clear `test/templates_c/v7/*`).

**Product Categories** (`bin/create-product-categories-module.php`): module in the Inventory menu, number series PC, fields name / number / parent category (self reference) / description, related list "Products" on a category. The Products field `productcategory` is converted **in place** from picklist (uitype 15) to a reference (uitype 10 → ProductCategories), keeping the field name and column so `DetailViewHeaderTitle.tpl` and others keep working; existing picklist values and the category text on products become category records and the products are re-pointed to their ids. The old picklist table stays but is no longer shown. The default reports in `PopulateReports.php` that list `productcategory` as text would now show ids (not changed). Services still use their own `servicecategory` picklist.

**Payments** (`bin/create-payments-module.php`): a payment points (`related_to`, uitype 10) at an Invoice, Quote, Purchase Order or Credit/Debit Note (SalesOrder). Fields: payment_no (PAY series), amount, payment_date, payment_method, reference_no, status (Completed / Pending / Failed), direction and customer/vendor (display-only, set from the document: invoice/quote = Received, purchase order = Paid, credit note = Paid (refund), debit note = Received). Rules live in `include/utils/PaymentUtils.php` (`Vtiger_Payment_Utils`) and `modules/Payments/PaymentsHandler.php`: the document must accept payments (Invoice: Approved/Sent/Credit Invoice/Paid; Quote: not Rejected; PO: Approved/Delivered/Received Shipment; note: Approved/Sent), amount > 0, and amount ≤ what is still outstanding (completed + pending payments count against the cap; failed do not). After save/delete/restore the handler refreshes the document: Invoice `received`/`balance` (and status → Paid when nothing is left, back to Sent when a payment is removed), Purchase Order `paid`/`balance`; quotes and notes only list their payments. The "Record Payment" button is added for all four modules in `Inventory_DetailView_Model` (only shown when `recordingProblem()` is null) and opens the payment form prefilled through URL parameters (`related_to`, `amount` = outstanding, date, status). The `received`/`paid` inputs in the line-item edit form are read-only so an invoice edit cannot overwrite what payments recorded.

**Gotcha:** fields with display type 2 (display-only) are not part of the entity insert, so a `beforesave` handler's `$entityData->set()` on them is lost; write them with SQL in `aftersave` instead (done for direction/account/vendor).

**Not tested / not done.** Payments on credit/debit notes and quotes, purchase-order paid/balance in the UI, import, workflows, portal, non-admin users, a printable receipt, payment totals on the invoice PDF, an online payment gateway. The browser pane refused the sandbox address mid-session, so these were checked over HTTP (scripted login, form posts, SQL), not by looking at the screens.

## Banking: Ledgers, Bank Accounts, Bank Transactions — 2026-10-09

Built after reviewing a competitor's vtiger customization (inERP): their Bank Accounts / Bank Transactions / Invoice Transactions / Accounting Heads modules, which keep balances through workflows and `cf_` fields. Ours keeps the rules in code. Skipped on purpose: e-invoicing/e-way bill, loyalty/coupons/POS, HR/projects. **Script:** `bin/create-banking-modules.php` (run `create-payments-module.php` first); uses the new shared helper `bin/lib/module-setup.php` (`registerEntityModule()`, `addCurrencyColumns()`).

**Model.** `Ledgers` = chart of accounts (group Assets/Liabilities/Income/Expenses/Equity, parent ledger; ~25 seeded). `BankAccounts` = bank/cash/card/wallet accounts with opening balance, `current_balance` (display-only, rebuilt from transactions) and a seeded "Cash in Hand". `BankTransactions` = one line In/Out per account with ledger, party, reference, narration, `reconciled`, `balance_after`, plus a hidden `transfer_pair` column and a `payment` link. Payments got a `bank_account` field.

**Rules** (`include/utils/BankUtils.php`, `modules/BankTransactions/BankTransactionsHandler.php`, `modules/Payments/PaymentsHandler.php`): amount > 0, active account, date not before the opening date; cash/wallet accounts cannot go negative (bank accounts may overdraw); a completed non-cash payment must name a bank account, and then **posts its transaction automatically** (In for Received, Out for Paid; pending/failed/deleted payment = no transaction); reconciled, payment-posted and transfer transactions cannot be edited or deleted from the transaction screen (change/delete the payment, or the whole transfer, which removes both sides); a payment whose transaction is reconciled cannot be changed or deleted; an account or ledger still in use cannot be deleted. Balances are rebuilt from the list after every save/delete/restore (O(n) per account, fine for now).

**Tools.** Bank account screens: "Transfer Money" (`BankAccounts&view=Transfer`, creates a linked Out/In pair), "Statement" (`view=Statement`: period, opening/in/out/closing, running balance, CSV export `action=StatementExport`, tick transactions reconciled via `action=Reconcile`, closing-balance-vs-books difference), Ledger Statement (`Ledgers&view=Statement`, includes sub-ledgers).

**Gotchas.** A module with currency fields (uitype 71/72) needs `currency_id` and `conversion_rate` columns in its own table or the list view dies with "result is not an object" (`addCurrencyColumns()`); display-only fields are written with SQL in `aftersave`; `beforedelete` handlers can veto a delete by throwing; the CLI needs `$currentModule` and the user's privileges loaded before `apply_field_security()`/saves behave like the web.

**Not done / not tested.** Ledger postings from invoices/purchases (no double entry yet: ledgers categorise bank transactions only), bank statement CSV import, opening-balance edits after transactions exist, multi-currency accounts, non-admin users, import of transactions, mobile/narrow screens (the browser pane was blocked, pages were checked over HTTP).
